# Отчет по практическому заданию 9: Асинхронность и корутины в Kotlin

## 1. Описание эксперимента

Было проведено сравнение двух подходов к загрузке данных (рейтингов) для списка из 10 приложений:
- Задержка сетевого запроса на каждое приложение: `delay(1500)` (1.5 секунды).
- Количество элементов в выборке: 10 приложений.
- Замер времени производился с помощью `measureTimeMillis`.

### Реализованные методы

1. **Последовательный (`loadRatingsSequentially`)**:
   Запрос рейтинга для каждого следующего приложения инициируется строго после завершения запроса для предыдущего:
   ```kotlin
   override suspend fun loadRatingsSequentially(ids: List<String>): Map<String, Float> {
       val ratings = mutableMapOf<String, Float>()
       for (id in ids) {
           ratings[id] = api.getRating(id)
       }
       return ratings
   }
   ```

2. **Параллельный без ограничений (`loadRatingsInParallel`)**:
   Все запросы запускаются одновременно с использованием `coroutineScope`, `async` и `awaitAll()`:
   ```kotlin
   override suspend fun loadRatingsInParallel(ids: List<String>): Map<String, Float> = coroutineScope {
       ids.map { id ->
           async { id to api.getRating(id) }
       }.awaitAll().toMap()
   }
   ```

## 2. Результаты измерений

| Подход | Время выполнения (мс) | Время выполнения (сек) | Относительное ускорение |
| :--- | :--- | :--- | :--- |
| **Последовательный (Sequential)** | **15 015 мс** | ~15.02 с | 1.0x (базовое) |
| **Параллельный (Parallel)** | **1 509 мс** | ~1.51 с | **~9.95x** |

---

## 3. Анализ результатов

1. **Последовательный подход**:
   - Общее время выполнения прямо пропорционально количеству элементов в списке: $T \approx N \times t_{request}$.
   - Для 10 приложений с задержкой 1500 мс суммарное время составило $15\,015\text{ мс} \approx 10 \times 1500\text{ мс}$.
   - Пользователь вынужден ждать завершения всех сетевых вызовов по цепочке, что блокирует отображение актуальных данных в интерфейсе.

2. **Параллельный подход**:
   - Все 10 корутин запускаются параллельно в рамках родительского скоупа `coroutineScope`.
   - Общее время определяется самым медленным запросом из всех запущенных: $T \approx \max(t_i) + t_{overhead}$.
   - В результате 10 запросов выполнились за $1\,509\text{ мс}$, что дало почти 10-кратное (9.95x) ускорение.

---

## 4. Выводы

1. **Structured Concurrency (Структурная конкурентность)**:
   - Использование `coroutineScope` гарантирует, что родительская корутина не завершится, пока не отработают все дочерние `async`-задачи.
   - Если один из запросов завершится ошибкой или родительский скоуп будет отменен, все параллельные корутины будут автоматически отменены, предотвращая утечки ресурсов.

2. **Масштабируемость и ограничения**:
   - Запуск параллельных запросов без ограничений (`async` на каждый элемент) эффективен при небольшом размере списка ($N \le 10..20$).
   - При больших объемах данных (сотни или тысячи элементов) неограниченный параллелизм может привести к исчерпанию пула потоков/памяти и блокировке со стороны сервера (Rate Limit / 429 Too Many Requests). В таких сценариях рекомендуется использовать `Semaphore`, `Channel` или пул с `limitedParallelism`.

3. **Отмена длительных операций (Задание 1)**:
   - Привязка операции эмуляции установки к `Job` внутри `viewModelScope` позволяет мгновенно реагировать на действие пользователя: при нажатии на «Отменить» вызывается `installJob?.cancel()`, корутина прерывается по `CancellationException`, и состояние интерфейса возвращается в `InstallState.NotInstalled`.
